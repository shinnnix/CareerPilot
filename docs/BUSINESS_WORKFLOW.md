# CareerPilot 业务闭环

CareerPilot 面向真实的 AI 实习求职过程：用户每天面对大量职位、重复填写表单和“岗位要求是否真的匹配”的判断成本。系统的目标不是展示若干 AI 技术，而是把一次投递从发现到复盘串成可追踪的工作流。

## 当前业务链路

1. 用户导入自己的简历、项目经历和学习材料，并导入或手动创建职位 JD。
2. 系统把文档保存为结构化字段、规范化原文和可检索 Chunk；用户可以按关键词或语义检索自己的证据。
3. 对职位进行匹配时，先检查城市、工作类型、到岗时间等硬条件，再比较技能和经历，并返回匹配分数、缺口和对应证据。
4. 用户决定申请后创建 Application，申请状态从 `saved`、`applied`、`interview`、`offer` 或 `rejected` 中按规则流转，避免只保存一条孤立的职位记录。
5. Agent 可以帮助搜索、匹配和生成准备材料。只读动作自动运行；创建申请、更新状态等会产生副作用的动作必须展示参数并等待用户确认，确认后通过已有 Service 执行并保证幂等。
6. 浏览器扩展读取当前网页表单的字段标签，向 CareerPilot 请求 Autofill Plan。计划为每个字段返回建议值、来源证据、置信度和人工复核标记；扩展只填充用户批准的字段，不自动提交申请。
7. 用户提交后记录结果、面试反馈和缺失技能，下一次匹配和材料生成使用这些反馈，形成“职位 → 申请 → 反馈 → 下一次投递”的闭环。

当前还提供两个面向持续使用的接口：`GET /api/v1/applications/follow-ups` 返回到期跟进事项，`GET /api/v1/applications/metrics` 返回申请漏斗统计；申请记录可以保存 `next_follow_up_at` 和 `interview_feedback`，因此投递后的行动和面试复盘不再只能写在自由文本里。

## 为什么这些模块属于同一个产品

- 职位库解决“我看到过哪些机会”，申请表解决“我对哪些机会采取了行动”。二者通过 `application.job_id` 连接，能统计漏斗和跟进提醒。
- 简历知识库解决“我有哪些可证明的经历”，匹配报告和 Autofill Plan 都必须引用同一批用户证据，避免模型凭空编造经历。
- Agent 负责理解意图和编排步骤，领域 Service 负责权限、事务、状态机和幂等。这样换模型不会改变核心业务规则。
- 浏览器填表不是独立的自动化脚本：它是申请记录的最后一公里，能把岗位字段映射到已确认的简历证据，并把填表结果回写到申请历史。

## 一次真实使用场景

用户每周收集十个 AI 实习岗位链接。CareerPilot 去重并保存 JD，先过滤不接受的城市和到岗时间，再把剩余岗位按 Python、RAG、评测等技能排序。用户打开一个高匹配岗位，系统展示“匹配原因”和“缺口”，从简历项目中选出可证明的经历，生成针对该岗位的项目要点和回答草稿。用户确认创建申请后，在招聘网站打开表单，扩展识别姓名、邮箱、项目描述等字段，回显来源和置信度，用户复核后填入。投递完成后把状态改为 `applied`，设置跟进日期；面试后录入反馈，系统把缺口沉淀为下一轮学习任务。

## 继续演进的优先级

1. 增加职位来源适配器和 URL 内容快照，记录抓取时间、来源和去重键，解决职位变化后无法复盘的问题。
2. 把跟进事项接入前端提醒和通知渠道，并基于申请事件时间线计算每个阶段的停留时间。
3. 为 Autofill 增加站点字段适配器、敏感字段默认人工确认、失败回滚和填充审计日志。
4. 用真实匿名 JD 建立困难负例，评估匹配排序和生成材料的事实一致性，不把小规模合成数据的分数当成线上效果。
5. 把 Embedding、重排和长 Agent 运行迁移到异步 Worker，并使用持久化 Checkpoint，支撑多用户并发。
